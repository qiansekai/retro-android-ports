# 移植笔记：KitKat 4.4.4 在新硬件上

> 中文译文。英文原文见 [kitkat.md](kitkat.md)。技术名词、代码、路径、命令与日志一律保留原文。

本实战手册讲述如何在 2014 年之后的硬件上把 AOSP KitKat（`android-4.4.4_r2`，KTU84Q，API 19）跑起来。起步于 Sony Xperia XZ Premium（`maple`，2017，MSM8998）；设备怪癖（含 TEST 1–49 的打通日志）见 [maple 怪癖](../../devices/maple/quirks.zh-CN.md)，分步构建见 [build/kitkat.md](../build/kitkat.zh-CN.md)。[Donut 实战手册](donut.zh-CN.md)是方法参照——本文是 KitKat 的差异部分。返回[进阶索引](../README.zh-CN.md)。
**在「Field lessons」标题以下的所有内容都已在 maple 上验证可启动（2026-10），但 [libhyb 一节](#libhyb-lessons-maple-2026-10-18-built-on-device-verification-pending)除外——该节于 2026-10-18 构建完成、尚待首次刷入验证；把它上面的各节当作最初的检查清单。**

## 实战教训（maple，已在设备上验证）

- **稀疏镜像会咬你两次。** `system.img` 默认构建为 SPARSE；用 `dd` 原样写完，分区就是无法挂载的垃圾（任何地方都不报错——init 只报告缺 `/system/bin/*`）。要么 `fastboot flash`（会自动去稀疏），要么先 `simg2img`，然后在刷入的分区上验证 ext4 magic（字节 1080 处的 `53 ef`）。设置 `TARGET_USERIMAGES_USE_EXT4`，否则 KitKat 会构建 yaffs2（在 GPT 设备上刷不进去）。
- **一条失败的 init 命令会静默地中止它所在的动作**（`do_mount` 返回 -1，没有 kmsg）。把挂载拆成独立的 `on init` 段，这样一个坏挂载杀不掉其余的。挂载语法是空格分隔的 flag + 一个尾部的 options 参数（`mount ext4 SRC /data nosuid nodev wait noauto_da_alloc,barrier=0`）；用逗号连写 flag 会被静默忽略，`wait` 永远不生效。
- **KitKat 的 init 里不存在 `wait_for_coldboot_done`**（它是无效命令，会中止它所在的动作）。优先使用裸 `/dev/block/sdXN` 节点（来自 TWRP 的 by-name dump）而不是 by-name 符号链接，从而彻底去掉时序变量——无需等待。注意：KitKat 上没有 `/dev/block/bootdevice/`；符号链接（如果确实想要）位于 `/dev/block/platform/soc/by-name/` 下。
- **重复 import 不是无害的**：同一文件第二次解析时，所有服务定义都会被 IGNORE（kmsg 里出现「ignored duplicate definition」）。更糟的是，如果 import 行本身丢了，文件会被拷进 ramdisk 但从不解析，里面的每个服务都静默未知（`start` 变成空操作——这一坑让 USB 整整停了一个周期：`init.maple.usb.rc` 没有它的 import）。只保留恰好一条 import 路径，并验证服务存在（`getprop init.svc.<name>`）。
- **先 mkdir 再挂载**：往不存在的目录挂载会静默失败 ENOENT（无 kmsg）。官方原厂 init.rc 不会替你创建 `/cache` 或 `/persist`——先在自己的 `on init` 段里创建它们。
- **在策略/上下文不匹配的内核上，init 里的 `write /dev/kmsg` 是观察不到的**（也不报错）。改用文件输出诊断（`dmesg > /data/...`、按 pid 的 `/proc` 快照），通过 TWRP 拉出来，不要靠 kmsg 标记。相关：4.4 内核没有 `CONFIG_LOGGER`，所以没有 `/dev/log`，原厂 logcat 是瞎的。给 liblog 打补丁让它回退到 `/dev/kmsg`（`patches/kitkat/system-core-liblog-kmsg-*.patch`），每个 `ALOG*` 就变成 `dmesg` 里一行 `<level>Tag[pid]: msg`——这也意味着被 [libhyb](../../advanced/software/libhyb.zh-CN.md) 加载的*新版* 32 位库会走旧的 liblog，于是它们的消息同样落到 `dmesg`。留意那一串 errno 连锁反应，它曾经害我们去追一个幽灵 EBADF（journal 文件相关的 helper 会靠沉默撒谎）。
- **首次启动要停掉的服务**（cooper 模式——全部是**临时**措施，修好真问题后重新启用）：`vold`，如果它会卡在陌生 userdata 上的 decrypt-wait（恢复条件：userdata 是 ext4 后我们的就能正常跑）；`rild`（没有 RIL 库 → 崩溃重启；保持关闭）；`healthd` 仅在 binder 故障让它变成 `critical` 时停掉（恢复条件：binder + `batterypropreg` 路径可用后我们的就能跑——没有它 BatteryService 会中止 system_server）。
- **FBE 的 userdata 必须重新格式化**（Lineage 的文件级加密对 KitKat 不可读；在 TWRP 里对 userdata 分区执行 `mke2fs -t ext4`——会毁掉现代安装，先拿到授权）。
- **仅在 64 位内核上跑 binder 是一次用户空间移植**，不是改配置：64 位干净的 UAPI 头（`binder_uintptr_t`/`binder_size_t` 为 `__u64`，protocol v8）、`Parcel` 的 8 字节偏移 + `hdr.type` + 指针转换、`IPCThreadState` 的 int64 读写 + `sizeof(uint64_t)` 偏移运算、servicemanager 本地结构体改成 64 位布局。搞错时的症状：`ioctl 0xc0186201 → EINVAL`（编号不被识别）、wpa_supplicant 链接时 `sme_*`/p2p/driver_cmd 未定义符号（需要 qcwcn 私有库）、事务静默解析错。一句话：「64 位 union 高半部分的垃圾会破坏查找」——每个字段都要赋值，不留未初始化 padding。
- **EGL 需要一个它不允许跳过的驱动**：KitKat 的 loader 会跳过 `libGLES_android.so`（「永远跳过软件渲染器」），在没有别的驱动时于 `eglGetDisplay` 里中止 surfaceflinger。要知道这个回退的极限：**libagl 只支持 ES1**——任何 ES2 客户端（动态壁纸、hwui 应用）找不到匹配的 config 就会死（`eglConfig not initialized`）。带一条真正的 ES2 路径，并为它缺席的情况保留一条非 GL 回退（EGL init 抛异常时走壁纸 canvas 路径，再加上下面的 Atlas backport）。
- **在 KitKat 上 EGL 驱动是按 readdir 选的，不是按 `egl.cfg`**：`Loader::MatchFile::find()` 先扫 `/vendor/lib/egl` 再扫 `/system/lib/egl`，找 `libEGL_*.so` 并取**第一个命中的**（已在服务端树的 `Loader.cpp` 里核实，约 265–350 行）；这个版本上 `egl.cfg` 在运行时是惰性的（它只是记录了布局）。于是*残留*的 `libEGL_emulation.so` 就成了不可预测的赢家，而且这个选择是一次性的：SF 按进程把它锁死，所以选错就意味着软件 GL，直到 SF 重启。要把探测做成确定性的（只构建恰好一个硬件 `libEGL_*.so`，把陈旧的模拟器库从 out 树里删掉），而不是去赌一个竞态。**绝不要设 `ro.kernel.qemu`**——它的存在会让同一个 loader 短路到 `libGLES_android.so` 并禁用 hwui。
- **退役的传输会留下它的变通做法**：进程内 [libhyb](../../advanced/software/libhyb.zh-CN.md) 设计（maple 2026-10-18）删掉了 glrenderd 的 socket，随之一并消失的还有有界应答/重连/socket 缓冲那套机制、readback presenter 和 EGL loader 补丁——GL 调用现在就是普通函数调用。当你更换传输方式时，把它曾经合理化过的那些变通做法扫一遍（它们依然「能用」，这正是它们能活下来的原因）：在宣布迁移完成之前，grep 整个 patch 集和 init 脚本里旧组件的名字。
- **两个翻转器会把 mdss 卡死**：只能有一个东西驱动 fb0 的偏移量。陷阱是「混合模式」：在 SF 已经选好渲染器（选择是按进程缓存的）之后再来一个翻转器跟 surfaceflinger 竞争——两者都翻，`yoffset` 失步，mdss 打出 `mdp ctl start failed`（EBUSY），面板冻结在开机画面上。修法是**顺序**，不是仲裁：持有 fb HAL 的那个组件必须是唯一的翻转器。libhyb 设计里 `gralloc.maple` 持有 fb HAL（SurfaceFlinger 通过它 post，从不 `FBIOPAN`），`fbpresentd` 在 `post-fs-data` 里、SF 首次 post 之前启动；旧的 glrenderd 设计则必须在 SF 首次 EGL 探测之前启动它的守护进程。
- **glrenderd 时代的 socket 教训（这一条，加上后面那组 readback/socket 内容，在 maple 上已退役，但在 poplar 上仍然成立，在此记录为 socket 传输式 GL 桥的模板）**：把每个「渲染器在不在？」探测都按真实启动延迟来定窗口。glrenderd 的冷启动（adreno 初始化 + 固件加载）很慢；5 秒的窗口错过了它，SF 就回退软件，并在这个进程的整个生命周期里不再重新考虑。大方地等（我们当时用 300 × 100 ms）。推论：让守护进程自身的启动保持快——一个「等 fb HAL 双缓冲，然后我们自己来做」的改动让 bind 花了 10 秒而不是 0.2 秒；在 glrenderd 模式下没人打开 fb HAL，所以直接立刻把 `yres_virtual` 翻倍（`FBIOPUT_VSCREENINFO`），否则守护进程采样到 `flips=0`，只做 memcpy 而从不 pan。
- **用能工作的那条路径所用的 ioctl 去翻转，而不是「显而易见」的那个**：在 maple 上 `FBIOPAN_DISPLAY` 返回成功，但 `mdss_mdp_overlay_pan_display` 打出 `unable to allocate base pipe` 且从不移动 `yoffset`——面板保持黑屏，而 fb0 和截图都是对的。官方原厂 gralloc 的 `fb_post` 用 `FBIOPUT_VSCREENINFO` + 新 `yoffset` 翻转；照抄之后 `/sys/class/graphics/fb0/pan` 就开始跳变。要在有活动时相信这个偏移（以及 `dmesg`），而不是 `mDisplayReady` 或那个 `idle_power_collapse` sysfs 字符串——后者撒了谎。一条声称 `FBIOPUT`「重做整个模式」的移植注释来自 drm 目标；在 fbdev 上它才是正确且廉价的翻转。
- **静态 UI 要关掉 mdss 空闲功耗塌陷**：MDSS MDP DT 节点里的 `qcom,mdss-idle-power-collapse-enabled` 会在空闲时把 MDP 断电；command-mode 面板随之变暗/变黑（无 scanout），下一次翻转被卡住，于是静态画面在触摸之前就消失了。从每个追加的 DTB 里剥掉该属性（`scripts/patch-maple-dtb.py`）并重新打包内核。用预编译的 `Image.gz-dtb` 时，DTB 以未压缩形式追加在 gzip 流之后（`zlib` 的 `unused_data` 能找到边界）；用 `dtc` 逐个反编译/重编译，或者干脆删掉那行属性——只改这一属性的 `dtc` 往返是安全的。
- **gralloc 的 stride 必须与内核的 `line_length` 一致**：mdss 会填充扫描行（1080 RGBA → maple 上 1088 px），而通用 gralloc 只按 4 字节对齐——每行都错切，面板上出现平行四边形。为 `HW_FB` 缓冲上报 `finfo.line_length` 作为 stride（`hardware-libhardware-gralloc-fb-stride.patch`）；用两种 stride 各解码一次原始 fb0 dump 来验证。
- **toolbox 在异种内核上会撒谎**：`sort` 段错误，`ps` 什么都不打印，`head`/`tail` 输出消失，`dmesg | tail` 吃 SIGPIPE（狂刷 debuggerd tombstone——改成写整文件）。shell 内建 + `cat`/`grep`/`echo` 可信。每个诊断工具都要在它运行的地方先验证，再相信它的输出。KitKat 的 toolbox 还缺 `restart`（用 `stop` + `start`）、`md5sum`、`tail`、`head`（TWRP 的 toolbox 全都有）；`cmp` 是有的。绝不要裸跑 `stop`（会连 adbd 一起杀——`stop zygote` 是安全的作用域内重启）。
- **没有 logcat 时的崩溃取证**（无 `CONFIG_LOGGER`，logcat 是瞎的）：native 栈用 `debuggerd -b <pid>`；`kill -3 <pid>`（SIGQUIT）把完整 JAVA 栈写到 `/data/anr/traces.txt`（要先 mkdir 它、`chown system`，否则 dump 静默失败）；Java 崩溃轨迹会累积在 `/data/system/dropbox/`（盯着它——有上限并会轮转）；`service call window <N>`，N 按 `IWindowManager.aidl` 的顺序数，可以调到隐藏的 WM 调用。
- **在线手术胜过重刷**：boot 分区可以在运行中的系统里 dd（`/dev/block/platform/soc/by-name/boot`）；单个 `/system` 文件通过 `adb remount` 推送（APK **和** odex 一起推——旧 odex 会静默获胜）；`adb reboot` 生效。整套系统重建要预留 5 GB 的 push+dd 循环。
- **僵尸遮罩会吃掉触摸**：如果 systemui 崩溃重启，每次死亡都会丢掉 keyguard 窗口，PhoneWindowManager 于是挂上一个全屏 KeyguardScrim（「Removing keyguard window (Did it crash?)」），它在 `mShowingLockscreen=false` 的情况下吃掉所有输入。通过 dropbox（崩溃栈）、`dumpsys window` 焦点、dispatcher 的 RecentQueue（证明事件确实到达）来诊断。修崩溃，不要修输入。
- **自动兜底（autowinch）安全网**：在远端且没有 adb 时，一个 15 分钟的 `sleep 900; setprop sys.powerctl reboot,recovery` 服务能把卡死的手机无人值守地送回 TWRP。一旦 adb 可信就立刻拆除（`stop`，然后移除）——否则它会杀掉正常的启动。
- **TWRP shell 的现实**：`/sdcard` 可能拒绝创建，而 `/data/media` 可用；`adb shell` 的 stdin 管道会失败（`Bad address`）；`adb push` 5 GB 镜像完全没问题；`by-name` 符号链接解析到稳定的 `sdXN` 节点；`console-ramoops` 跨重启保留内核日志（跑几小时后会损坏）；`/proc/config.gz` 直接回答内核问题。
- **CPU 变体**：对 Kryo 来说 `cortex-a15` 是 KitKat 时代的正确选择（HW atomics）。一次 kuser-helpers 恐慌在现场被证伪——开机后的 32 位进程能跑；TWRP 侧的 SEGV 是环境问题（recovery ramdisk 里缺 `/system/bin/linker`，破坏 PIE 解析）。
- **Dalvik 堆档位是必需的，不是调优**：不继承 `phone-*-dalvik-heap.mk`，构建就带极小的默认值，system_server 在验证第一个大 APK 时 OOM（`JarUtils.verifySignature` 里的 `OutOfMemoryError`，每次生命周期都是同一个栈，dalvik-cache 从不填充）。按 RAM 选档位（4 GB → `phone-xhdpi-2048`：192m/512m）。相关：eng 构建用 `WITH_DEXPREOPT`，否则首次启动要在设备上 dexopt 每个 jar/apk。
- **`system.prop` 是追加到 build.prop**（`PRODUCT_COPY_FILES ... :system/build.prop` 会合并进生成的文件），所以 `PRODUCT_PROPERTY_OVERRIDES`（堆等）能和它并存无碍。
- **make 在陈旧性上撒谎**：改 product 的 `.mk` 不会重新触发 `systemimage`/`bootimage`（输入变了却提示「Nothing to be done」）。删掉产物重建，然后校验**内容**（解包 ramdisk、grep 那些 jar），绝不要看时间戳。
- **mkbootimg 不需要回移**，对 base-0 + `Image.gz-dtb` 而言（已验证的几何：base 0+0x8000，pagesize 4096）。预想的补丁并不需要——动手造它之前先验证那些担忧。
- **无上限的渲染器应答会导致永久 UI 冻结**（maple TEST 32）：一次同步 GL 调用就是一次 socket 往返；一旦渲染器停止应答，调用方就永久阻塞——对 systemui 来说这就是冻结的 UI（`recvfrom` 卡在 `SocketStream::readFully` 里）。给每个等待加上限（`SO_RCVTIMEO`，可用 prop 调），把 timeout/EOF/EPIPE 当作死亡，**原地**重连（绝不释放连接——会 use-after-free），发送用 `MSG_NOSIGNAL`，并让已死的 `writeFully` 报告成功（一次失败的 `writeFully` 会 NULL 掉预编译编码器要 memcpy 的缓冲）。渲染器侧：给读缓冲设上限，一次解码只处理一条消息，丢弃客户端。
- **fork 出的应用不得共享 GL socket**（同批）：TLS 连接会跨 zygote fork 被继承，随后多个进程在同一个流上交错写（帧定界永久丢失）。在 `HostConnection::get()` 里按 pid 变化重新拥有连接——用文件级 static，绝不新增成员（inline 的 `alloc()`/`flush()` 把成员偏移硬编码进了每个已构建的编码器库）。
- **「卡在开机画面」按 USB 状态分型**（maple TEST 32）：adb 活着 + 面板画面滞留 = 显示交接卡死（系统已起来）；**完全没有 USB = 用户空间之前的挂起**（bootlog 从未写出——查 `/data` 的 mtime 确认）。没 USB 那一型经一次 TWRP 往返（在 TWRP 里 `adb reboot`）恢复了——重刷之前先试这个；强制断电会丢 ramoops，所以 pstore 解释不了这个挂起。
- **姊妹设备的修复集是参考，不是配方**：两个 msm8998 KitKat 移植（maple/poplar）在 fb0 翻转 ioctl 上得出了**相反**的结论（`FBIOPAN_DISPLAY` vs `FBIOPUT_VSCREENINFO`——各自在自己的设备上验证过），在由谁来翻倍 `yres_virtual` 上也相反。以设备上的证据压倒跨设备的建议；每个坑都要到目标机上重新验证。
- **可借用的修复集仍然需要读懂，而不是照抄**（maple TEST 33，移植执行）：poplar 那一套里有三件事之所以能成立，靠的是它没有随附发布的代码，或者本身就是残缺的：(a) 它的重连设计要求在流被标记为死亡时**关闭** socket——它发布的 `SocketStream.cpp` 只做标记然后返回，于是 `valid()` 一直为真，`reconnectIfDead()` 永远不会触发；要么关掉 fd（并置为无效），否则这个「自愈」流永远不会自愈；(b) 渲染器在解码前会读一个**每连接握手字**（`RenderServer::Main`：一个 `clientFlags` uint）——首条连接从 `HostConnection::get()` 拿到它，所以原地重连必须重放它，否则渲染器会把第一条 GL 命令当成 clientFlags 吃掉（或者触发 `IOSTREAM_CLIENT_EXIT_SERVER` 退出）；(c) `RenderThread` 的下线路径调用 `peerPid()`/`shutdownStream()`，而这两个不在那套里——把它们追加到 HOST 的 `IOStream` 的**所有既有虚函数之后**（guest 的 vtable 槽位不能移动），用 `SO_PEERCRED` + `SHUT_RDWR` 实现（两者在 KitKat bionic 和 NDK 里都有）。
- **写侧也要加上限**：卡住的渲染器不再排空它的 socket；`send()` 于是永久阻塞，所以光有 `SO_RCVTIMEO` 救不了合成器。设 `SO_SNDTIMEO`，每次 send 都带 `MSG_NOSIGNAL`，并让守护进程 `signal(SIGPIPE, SIG_IGN)`——一个在应答中途死掉的 guest 不能把渲染器杀掉（它静默的 SIGPIPE 死亡就是经典「莫名其妙回退到软件 GL」的成因）。
- **调高 `rmem_max`/`wmem_max` 不等于「设置 socket 缓冲」**（maple TEST 34）：每个 socket 的默认值是 `net.core.{r,w}mem_default`（这个内核上是 208 KB），与 max 无关——已存在和新创建的 socket 都保持这个值，直到有人真的 `setsockopt(SO_SNDBUF/SO_RCVBUF)`。在 AF_UNIX 流上，在途数据是记在发送方的 `SO_SNDBUF` 上的，所以一个推一帧命令流（>200 KB）的 guest 会在帧中途阻塞在 `send()` 里，guest 与渲染器锁步推进（实测：没有别的东西饱和，GPU 在最低频，CPU 空闲）。两端各设约 8 MiB——发送方在 connect/重连时设，接受方紧跟 `accept()` 之后设；缓冲是按需分配的，空闲时这个上限不花任何代价。姊妹移植的文档声称「SocketStream 申请 8 MB」可能只是一厢情愿：读代码，别读文档（发布的 poplar SocketStream 什么都没申请）。
- **keyguard 窗口上的 `userActivityTimeout` 把息屏封顶在 10 秒**（maple TEST 33）：AOSP 的 `KeyguardViewManager` 在 keyguard 窗口的 `LayoutParams` 上设 `AWAKE_INTERVAL_DEFAULT_MS`（10000 ms），WMS 把它作为 `mUserActivityTimeoutOverrideFromWindowManager` 交给 `PowerManagerService`——生效的超时变成 `min(setting, 10000)`。在一个刚刚有了可用 lights HAL 的移植上（在那之前背光从不变化，所以没人注意到显示状态），面板现在会在最后一次触摸约 10 秒后可见地变黑。这是官方原厂行为，不是挂起：电源键能唤醒。追它之前先看 `dumpsys power | grep mUserActivityTimeoutOverride`。
- **Sony msm8998 暴露两个独立背光节点**：mdss led（`/sys/class/leds/lcd-backlight`，AOSP 惯例）和 PMIC WLED（`/sys/class/leds/wled`，TWRP 驱动的是这个）。写一个**不会**改变另一个的值（在实机上探测过，两者 max 都是 4095）。lights HAL 应该把同一个缩放值写进两者——真正接到面板的那个生效，另一个是惰性的。屏幕亮着时（`mScreenOn=true`；睡眠的屏幕按设计读 0）用 `settings put system screen_brightness N` + 读两个节点来验证亮度。
- **协议文件没动时，重建渲染器是安全的**（glrenderd 时代，为 poplar/遗留引用保留）：「绝不单独重建 glrenderd」这条规则针对的是由 `.in` 文件生成的 `*_enc`/`*_dec` 编解码表——只要那些没变，重新生成的表就完全相同，部署的 guest `*_enc.so` 与之匹配（maple TEST 33 从同一棵树重建了 glrenderd，面板正常起来）。无论如何都把已知良好的二进制留作备份。
- **在 framebuffer 支撑的渲染器上，post readback 是每帧成本的底线**（maple TEST 35；libhyb 替换掉的设计——在 maple 上已退役，仍是 poplar 的 glrenderd 的形态）：guest 在宿主 GPU 上合成、面板由 fb0 喂，那么每个上屏帧都要付出一次同步 `glReadPixels`（1080p 时约 9–10 ms）外加一次拷进 presenter。把 readback 直接弹进 presenter 的 staging 槽（poplar 的 A6：`FrameBuffer::setPostReadback` + 一个槽选择器 + 一个面向 fb0 的 presenter），那次额外的全帧拷贝就消失了——约 1–2 ms/帧，不增加延迟。把 readback 藏到一个晚一帧才 map 的 PBO 后面，在这个 Adreno 驱动上实测**更慢**（13 fps vs 31–35 fps——map 的代价比它藏起来的同步 readback 还高），所以先测量再假设。另外，把 readback 保持在面板页**之外**（fb0 page 竞争 / vblank 耦合——poplar 试过并回退了）。
- **wifi 需要定义它的 init 服务，而不只是配好它的 BoardConfig**（maple TEST 36）：KitKat 的 wifi.c 用 `ctl.start wpa_supplicant` 启动 supplicant，而当该服务不存在时这是静默空操作——而这棵树一个都没定义。BoardConfig（`BOARD_WLAN_DEVICE := qcwcn`，NL80211，`lib_driver_cmd_qcwcn`）只保证 supplicant **可链接**。把 hammerhead 那一套发出去（`wpa_supplicant`、`p2p_supplicant`、`dhcpcd_wlan0/p2p`、`iprenew_*`，带上 `-O.../sockets` 控制目录，以及必须在服务起来时就已存在的 `-I..._overlay.conf` 文件），再加 wifi.c 从不创建的目录（`/data/misc/wifi/sockets`、`/data/misc/dhcp`）。`lib_driver_cmd_qcwcn` 是**静态**库——它不在 `/system/lib` 里是正确的。分型诊断：驱动已加载（`/sys/module/wlan`、`/dev/wlan`）但没有 wlan0、也没有 `/sys/class/ieee80211` phy = 固件/QMI 握手从未发生（在 qca_cld3+icnss 上 WLFW 侧在 modem 那边；一个从未启动的 modem 也可能挡住 wifi——承诺之前先验证）。
- **没有声音的声卡是 DT + 守护进程的问题，不是 HAL 的问题**（maple TEST 36）：`--- no soundcards ---`，且没有任何 tavil/tasha/wcd/slim 探测行、`/sys/kernel/debug/asoc/*` 为空，意味着 machine driver 在它来得及打日志之前就在 defer（WSA/wcn-btfm 的等待是 `dev_dbg`，没有 dynamic debug 看不见）。HAL 照写（声卡缺席时静默安全，让 mediaserver 保持活着），但先修内核侧，按 CHARQUIRKS 的顺序：从 sound 节点上剥掉 BT slimbus dai（msm8998 上的 `qcom,wcn-btfm` = pdx203 的 `qcom,wcn-bt = <0>`；`scripts/patch-maple-dtb.py` 把 mdss 和这个一起做，幂等，逐 DTB 字节校验）、设 `service_locator.enable=0`（设 =1 时声卡在 pdr 上等了约 5 分钟）、把 adsp 固件放到 `firmware_class.path` 指向的位置（找不到时 ueventd 的用户态 helper 每个文件卡约 60 秒——这个延迟就是线索）、把 dsp/slpi 的重启等级钉到 RELATED（SYSTEM 会让 dsp 一崩就手机 panic）。如果声卡还是不探测，WSA881x 功放（`qcom,wsa-devs`）是下一个 defer 嫌疑——剥掉它们之前先看有没有任何 wsa/swr 探测行（扬声器需要它们）。
- **绝不要 dd 正在运行的 system 分区然后继续用 shell**（maple TEST 37b）：在已挂载的 `/system` 底下写裸镜像会破坏运行中的 libc（`CANNOT LINK EXECUTABLE: could not load library "libc.so" ... empty/missing DT_HASH`）——之后每条命令都死。推送镜像、在分区上验证 md5，然后**立刻**重启，不要再跑任何别的。（已验证：`4b8539ac…` 5 GB，`dd` 38 秒，分区上 md5，紧接着 `adb reboot`。）
- **规划任何 QMI 用户空间之前先查 kallsyms 里的 QRTR**（maple TEST 37）：`grep -c qrtr /proc/kallsyms`，带正对照（`binder`、`msm_ipc_router` 必须命中）。为 0 意味着任何直接链接 `libqrtr.so` 的东西都跑不了（maple：`tftp_server`、`qrtr-ns`）——但先查客户端库：厂商的 `libqmi_cci` / `libqmi_csi` 是双传输的（`qcci_`/`qcsi_ipc_router_ops` 加上 `qrtr_ops`，运行时探测），会回退到旧式 IPC Router，所以「任何现代 QMI 守护进程都永远跑不起来，chroot 与否」这个判断太重了（Taimen 映射 §corrections，2026-10-18）。旧式 IPC_ROUTER（`msm_ipc_router` 线程、`sysmon-qmi` 触达 ADSP SSCTL）和 SMD FastRPC（`/dev/adsprpc-smd`）已证明可用。
- **读正在运行的内核，不要读 defconfig**（maple TEST 36）：`/proc/config.gz` 是地面真相（`4.4.302-whatawurst+` 内建了 `CONFIG_QCA_CLD_WLAN=y` 以及完整的 tavil/WSA/QDSP6 集，而 lineage-17.1 的 defconfig 还写着 `=m`）。板级注释也用同样方式从 BCM43xx 更正为 WCN3990/cherokee（bluetooth 分区上的 BT tlv 名字与之吻合）。
- **新的 audio HAL 必须填满整张 ops 表，而不只是 open/write**（maple TEST 36）：当 HAL 让 `dev->init_check` 为 NULL 时，mediaserver 在 `AudioFlinger.cpp:1349` 调用它而 SIGSEGV（tombstone：`AudioPolicyCompatClient::loadHwModule` → libaudioflinger `loadHwModule_l` → pc 0）。给框架能触达的每个指针都赋值——device 的 close/init_check/volumes/mutes/mode/mic/params/input_buffer_size/streams/dump，两条 stream commons（rate/buffer/channels/format/standby/dump/params/effects），out（latency/volume/write/render_position/write_timestamp）和 in（gain/read/frames_lost）。用不到的旋钮返回 `-ENOSYS` 或中性值（照抄 `hardware/libhardware/modules/audio/audio_hw.c`，那个通用 stub）。通过 `/data/tombstones` + `addr2line` 对着 `out/.../symbols/...` 诊断（cooper 的 32-vs-40 字节教训，同样的工具）。
- **`PRODUCT_COPY_FILES` 发不了空目录**（maple TEST 41，2026-10-17）：用 `find . -type f` 去 stage 一棵目录树（`stage.py` 的惯用法）会静默丢掉每一个空目录（`dev`、`proc`、`sys`、`data/...`）。任何要在运行时于只读分区里 `mkdir` 挂载点的设计（chroot + bind-mount 布局）随后就会 `EROFS`，它的 bind 失败 `ENOENT`，守护进程重启循环，而一次性的 hw-vs-software GL 探测把软件路径锁死在这个进程的整个生命周期里（个位数 fps，直到 SF 重启）。修法：运行时在可写的 tmpfs 上造挂载点——`hwchroot` 在 `/dev/.glr` 下组装 glrenderd 的 chroot，并把真实条目 bind 上去；`<root>` 里面什么都不写。
- **staged 二进制会静默回退成 staging 目录里的那个**（maple TEST 41；对 `maple-hyb/` + `maple-bin/` 仍是规则，见 [libhyb](../../advanced/software/libhyb.zh-CN.md)）：一个重建的守护进程被在线推到了设备上，但 staging 目录没有刷新，于是下一版系统镜像把旧二进制和新 guest 库一起发了出去——跨构建的协议不匹配让守护进程 5 分钟内崩了约 3 次（FORTIFY destroyed-mutex，`glBindTexture`/`TexImage` 里的 SIGSEGV）。在同一次改动里刷新 staging，用哈希验证部署的实体，并让新构建打印一个标记（一个 stats/log 字段），这样「正在跑的是哪个二进制」就只是一条 `dmesg | grep`。
- **KitKat init 服务重启的事实**（maple TEST 41，直接来自 `system/core/init/init.c`）：崩掉的服务只在 `time_started + 5` 之后才重启（`restart_service_if_needed`，约第 418 行），所以一个崩溃循环的周期 ≥5 秒；`setprop ctl.restart <svc>`（`service_restart`，约第 400 行）在运行中意味着 stop+start，不在运行时就是单纯的 start，正在重启时是空操作。重启对 property 触发器不可见（4.4 的 init 没有状态通知），所以一个必须对别的服务重启做出反应的组件需要一个带内标记文件。
- **init 触发器不会等它启动的服务**（maple TEST 41）：post-fs-data 里的 `start fbpresentd`（或任何服务）在进程 fork 出之后即返回，init 立刻推进到下一个触发器（`on boot` → `class_start core`）——maple 启动时 surfaceflinger 的进程只比被启动的那个服务的晚几毫秒出现（这是被一个错误假设「SF 在跑」就等于「守护进程已重启」的探测抓到的）。早期触发器期间，绝不要从进程存在来推断服务状态。
- **跨时代属性写入会 exec 宿主机的 `setprop`**（maple TEST 41）：用现代 NDK 静态构建的 helper 仍然能在旧版本上跑，但它带的 property 客户端期待 8.x 之后的 `/dev/__properties__` 布局，而不是 KitKat 的单文件区域——hwchroot 于是为 `ctl.restart` 去 `fork`+`exec` 宿主机的 `/system/bin/setprop`（已在设备上验证）。同样的招数适用于任何必须去戳远古版本 init 的现代侧 helper。

## libhyb 教训（maple，2026-10-19 在实机上验证）

这是 glrenderd 的进程内替代方案——把 Lineage 22.1 闭包里的 Adreno 540 驱动 + QTI gralloc1 装进 KitKat 的进程里。完整说明见 [libhyb](../software/libhyb.zh-CN.md)；采纳记录（哪些 Taimen 的补丁被采用、跳过或排队）见 [taimen-kitkat-mapping.md](../taimen-kitkat-mapping.zh-CN.md)；设备日志见 [maple 怪癖](../../devices/maple/quirks.zh-CN.md) TEST 49。可复用的教训：

- **更新一些的 32 位厂商驱动可以在旧 Android 上被进程内调用。** C 层的 EGL/GLES ABI 在这个跨度上是稳定的；需要搭桥的只是 (a) 新库 import 的 bionic 符号和 (b) 缓冲格式。带一个 loader + 一张 hooks 表，驱动的真实入口点就变成普通函数调用——没有 socket、没有 readback、没有 chroot，「只能有一个翻转器」的问题也塌缩成「gralloc HAL 持有 fb0」。
- **新旧边界要一个名字一个名字地定。** loader 把一份固定的宿主清单（`libc`、`libm`、`libdl`、`liblog`、`libcutils`、`libz`）解析到旧系统自己的库上，其余一切从闭包里 stage 进来。正是这一点让进程里只有一份 allocator、信号处理和日志——也意味着*新*库的 `ALOG*` 输出走的是旧 liblog，所以旧侧的一个日志修复（上面那个 `/dev/kmsg` 回退）会把驱动的日志一并点亮。
- **用 `readelf -d` 从真实的根出发发现闭包，然后再加一趟处理运行时的 `dlopen`**（`eglSubDriverAndroid`、`libq3dtools`、gralloc 模块）：光靠链接器图会漏掉 HAL 按名字加载的东西。让 staging 保持确定性（工具已经这么做了），并把 stage 了什么、拒绝了什么打印出来，否则下一个人得手工再走一遍。
- **面向内核的常量要从目标机自己的内核头文件重新推导**，绝不从姊妹移植的副本里抄：原子提交的 pipe 编码（`pipe_ndx`）和 `msm_mdp*.h` 的结构体布局都来自这个内核的 `include/uapi/linux/`，然后被 vendor 进设备树，这样用户空间构建和内核就不会漂移。
- **只有 64 位的内核路径需要一个树外二进制**——KitKat 的构建系统只产出 32 位二进制，而至少一个 MDSS ioctl 的 32 位兼容路径是致命的（Taimen 的移植；在 maple 上待验证）。用 NDK（`-static`，aarch64）构建 presenter，并把它 stage 到 `vendor/sony/<device>-bin/` 下、**在设备树 rsync 路径之外**，这样 `sync-device-tree.sh --delete` 吃不掉它。
- **`LOGI` 不是 KitKat 的宏。** 设备树代码会在*链接*时以 `undefined reference to 'LOGI'` 失败，因为未展开的名字变成了隐式函数调用；用 `ALOGI`/`ALOGE`（`cutils/log.h` → `log/log.h`），就像 `hardware/` 那样。
- **从 `PRODUCT_*` 里删掉文件并不会把它们从 out 树里删掉。** `mkuserimg.sh` 打包的是 `out/target/product/<device>/system` 里现在有的东西；去掉一条 `PRODUCT_COPY_FILES`/`PRODUCT_PACKAGES` 条目只是让旧文件（root 所有，来自容器构建）继续留在镜像里。退役 glrenderd 设计之后，第一个 libhyb 镜像仍然带着整个 25 MB 的 `/system/glr/` chroot、模拟 GL 库和 `/sbin/glrenderd.sh`。每当删掉一个组件，就要从 out 树里删掉那些陈旧路径（或者整个 `system/` 目录）并重建镜像——而且绝不要拿「我把补丁删了」来相信镜像里到底有什么（maple TEST 49）。
- **先在这个 dlopen 的本地组里解析符号，再到 KitKat 的全局符号里找。** 两个相机模块可以定义同名但大小不同的全局变量（`g_cam_log`）；绑错副本就会踩坏内存，而且离加载点很远。Taimen 是用 **gdbserver 硬件观察点**找到写者的；我们的 `linker.c` 实现了同样的顺序（hooks → 本地组，从 dlopen 根做广度优先 → 已加载的库 → KitKat）。
- **加载期的二进制补丁表在能自我校验时是正当的兼容工具。** 新版 libbinder 的 `ServiceManagerShim::getService` 对每个缺失的服务都要等 5 秒（每次开相机都这样）；`linker.c` 只在四个原始字节匹配时把 `movw r5, #5000` 改写成 `#0`，不匹配时就大声打日志。`HYB_TRACE_SYM=<symbol>` 和 `HYB_TRACE=1` 用来在闭包行为不对时追踪解析和 hook——把它们跟着 loader 一起移植。
- **现代内核把厂商节点只交给 root，而进程内驱动已经不再是 root 了。** `/dev/kgsl-3d0` 和 `/dev/ion` 起来时是 `root:root 0600`；chroot 时代的设计从不关心这个（它的渲染器以 root 跑），但 `libhyb` 风格的驱动跑在 surfaceflinger 里（uid `system`）、也跑在每个 app 进程里：`eglInitialize` 返回 `EGL_BAD_ALLOC`（`Adreno-GSL: open(...) failed: errno 13`、`qdgralloc: Failed to open ion device`），SurfaceFlinger 以 KitKat 那句笼统的 `no suitable EGLConfig found, giving up` 中止——注意 `eglChooseConfig` 对**任何** `eglInitialize` 失败都报*零*个 config，所以 EGLConfig 的属性是误导线索。在 `ueventd.<device>.rc` 里修（两个节点都给 `0666 root root`；group 规则覆盖不到 app 的 uid，而这些移植跑的是 SELinux permissive，所以 DAC 就是全部故事）。运行时的 `chmod 666` 不用重刷就能验证这一点。
- **在没有 logd 的内核上，服务的 `ALOG*` 输出需要一个可写的 `/dev/kmsg`。** 旧 init 把每个 init 启动的服务的 stdout/stderr 都指向 `/dev/null`，而旧 liblog 的兜底 sink 就是 `/dev/kmsg` 本身——但这个节点是 `0600 root`，`open()` 一旦 EACCES，liblog 就静默地把 `write_to_log` 指向 `__write_to_log_null`。结果：root 进程和 zygote 的子孙进程有日志（它们自己 open 或继承了 kmsg fd），init 启动的服务却全程沉默，而那些缺失的行看起来像卡死。修法：在 ramdisk 的 `init.rc` 里 `chmod 0622 /dev/kmsg`（服务可写，读仍限 root——反正 `dmesg` 需要 CAP_SYSLOG）。验证方法：两边都跑 `log -p i -t TESTTAG hi`，或者以 root 手工跑一次那个服务（`stop surfaceflinger; surfaceflinger`），看它本来会说什么。
- **KitKat 的 init.rc 在 surfaceflinger 上挂了 `onrestart restart zygote`。** 所以 SF 一崩溃循环，每隔几秒就把 zygote 杀掉，框架永远跑不完 `preloadClasses`：一个图形 bug 表现为 zygote/preload 启动循环 + SF 中止 + 「起不来」。当 KitKat 移植的 zygote 在循环重启时，先查 SF。
- **新版 32 位闭包库带 TLS 重定位，旧 loader 必须实现它们。** `R_ARM_TLS_DTPMOD32`（以及 `DTPOFF32`）配上 filesz 为 0 的 `PT_TLS`（纯 `.tbss` 对这些库来说是常态）需要一张模块表和真正可用的 `__tls_get_addr`；一个拒收未知类型的 loader 会让整个 `dlopen` 失败，通常就死在 EGL 驱动上。如果 loader 在那儿停下，日志里只会出现*第一个*重定位类型——所以在断定 TLS 不必要之前，用 `readelf -r` 把闭包里的 DTPMOD32/DTPOFF32/TPOFF32 全查一遍，顺便查 `__emutls_get_address`（形态和实现见 libhyb 的说明）。
- **绕过 framebuffer 的上屏路径会让 fb0 回读变瞎。** 零拷贝提交下 fb0 的内存从来不会被写，所以一个「dump 再解码」的「它在渲染吗？」测试装置，会在驱动得好好的面板上看到全零帧；为验证保留（或造）一条拷贝回退路径，并用它做几何检查（stride、错切），而实时检查靠 presenter 的 fence/速率日志。

## 音频（ACDB）教训（maple，2026-10-19 在实机上验证）

高通的内核音频驱动（q6asm/q6afe/q6adm）是**校准的使用方**：在流/端口启动时，它们去查一批 ACDB 块，而那些块是由用户空间的 loader 推进 `/dev/msm_audio_cal` 的。在一个旧用户空间没有 loader 的移植上，块查找会失败（`send_afe_cal_type: cal_block not found!!`、`q6asm_send_cal: cal_block is NULL`），播放是静音的、而 PCM 处于*运行*状态——dsp 只是以快于实时的速度把缓冲排空。那个 loader（`libacdbloader.so`）是一个 Android 15 时代的库，所以和 GPU 驱动一样可以套用进程内的招数。现场日志：maple 怪癖 TEST 50；HAL 在 [`devices/maple/kitkat/audio/audio_hw.c`](../../../devices/maple/kitkat/audio/audio_hw.c)。

- **cal 块归 loader 的 fd 所有。** 它们出现在 loader 打开 `/dev/msm_audio_cal` 的时候，在它退出时消失，所以一次性发射的 helper 不够——加载它们的东西必须常驻（HAL 在 mediaserver 的整个生命周期里持有这个句柄）。一个常驻的测试 helper（`acdbtest --v3 --hold`）就是在把它接进 HAL 之前先证明这条生命周期规则的办法。
- **内核里的契约是 app-type cfg 控制项。** 在路由之前，HAL 把 `Audio Stream 0 App Type Cfg` 设为 `[app_type, acdb_id, sample_rate]`（KitKat 的 `mixer_ctl_set_array` 支持 INTEGER 数组；这个控制项有 128 个槽位，写入会把其余清零，与官方原厂的三值形式一致），然后向 loader 要匹配的块：`acdb_loader_send_audio_cal_v3(acdb_id, dev_type=1, app_type, rate, 0)`。顺序很重要：cfg → cal → route → `pcm_open`，因为 afe-cal 是在后端端口启用时应用的，而 asm-cal 是在 PCM 打开时应用的。
- **`hw_platform` 决定 acdbdata 目录，这个目录名不是装饰。** loader 从 `/sys/devices/soc0/hw_platform` 拼出 `/vendor/etc/acdbdata/<hw_platform>/`（workspace 文件 + 顶层 `.acdb`）——在 maple 上是「MTP」——而上游的树常常把这些文件放在 form-factor 或 OEM 目录下（yoshino 是 `Sony/`）。把数据 stage 到设备实际报告的那个名字下，否则 loader 会在没有 workspace 的情况下初始化，校准是空的。
- **这个节点默认只有 root 能访问；必须要一条 group 规则。** 驱动创建的 `/dev/msm_audio_cal` 是 `root:root 0600`，而 loader 跑在 mediaserver 里（uid `media`）。这个 EACCES 在 open() 时是静默的，只在后来表现为一个看起来无关的 init 失败（`ADIE RTAC INIT` → `allocate_cal_block failed!` → `Cannot allocate memory!` → `-ENOMEM`），所以在怀疑数据之前先查 DAC。`ueventd.<device>.rc`：`0660 media audio`。
- **等声卡起来之后再初始化 loader。** mediaserver 打开 HAL 的时候，dsp 还要好几秒才启动，所以声卡还不在 `/proc/asound/cards` 里：open 时什么都不要缓存（在那里缓存一个 NULL mixer 会让路由变成空操作，而 `pcm_open` 仍然在后来出现的声卡上成功），loader 的初始化也要推迟——在没有 codec 的情况下初始化会以 ADIE RTAC init 的 `-ENOMEM` 结束。在第一个流到来时重新探测并打开。
- **KitKat 的 tinyalsa `pcm_write`/`pcm_read` 收的是字节数，不是帧数。**（`external/tinyalsa/pcm.c` 自己会把计数除以帧大小。）传帧数会只写进每个立体声 16 位缓冲的四分之一、丢掉其余部分，dsp 渲染出一段被切碎的信号，读起来可以像「有 PCM 在跑却是静音」。同一套 API 在别的 tinyalsa 副本里是 `pcm_writei` 那样的帧语义，所以在移植一个 HAL 之前先读那棵树自己的 `pcm.c`。
- **dynamic debug 能把用户空间和 dsp 分开。** 在这些移植上手工挂 debugfs（`/d` 是 `/sys/kernel/debug` 的符号链接，但没人挂它：`mount -t debugfs none /d`），然后 `echo "file msm-pcm-q6-v2.c +p" > /sys/kernel/debug/dynamic_debug/control`（再加上 `q6asm.c`、`q6adm.c`、`q6afe.c`、`msm-pcm-routing-v2.c`），每一次 copy/cal/拓扑步骤都会带着字节数落进 dmesg——正是它把「HAL 是静音的」变成了「HAL 只写了缓冲的 1/4」。
- **一个框架级的探针值得它的构建时间。** 一个树内的小 `AudioTrack` 工具（`audiotrack_test`，由设备树构建）走 AudioFlinger → HAL，这是 tinyalsa 工具做不到的；把它配上一次采集，并检查音调的能量带，而不只是「有没有声音」。采集的兄弟工具（`audiorecord_test`，同目录）通过 AudioFlinger 录成裸 S16_LE，并打印每秒的 peak/rms；同时播一个音调并录下来（`audiotrack_test 8 48000 0.8 & sleep 1; audiorecord_test 6 48000 /data/local/tmp/loop.raw; wait`）就是端到端回环，在宿主机上用 [`scripts/analyze-rec.py`](../../../scripts/analyze-rec.py) 分析（peak/rms、主频、卡顿边带；需要 numpy）。
- **这个年代里 `ACDB_DEV_TYPE_IN` 是 2，不是 0。** qcom HAL 的头（`hardware/qcom/audio/hal/audio_hw.h`）定义 `ACDB_DEV_TYPE_OUT 1` 和 `ACDB_DEV_TYPE_IN 2`；用 0 发 TX 校准会让 loader 打出 `ACDB -> Device is not RX or TX!acdb_id = %d` 并返回一个非零拒绝（65–67），而同样的 id 用 2 就返回 0 并把块推上去。loader 的设备表是一张硬编码的 RX/TX 表，不是自由形式的 id：speaker 15、headphones 10 和 speaker+headphones 799 是 RX 项，而 mic 一族 4（handset）、8（headset）、6、9、35、131、143、152 全都能用 dev_type 2 过。在相信一个猜测之前先扫一遍——`acdbtest --scan`——但要知道它的 TX 发送会加载一些块，那些块会让采集一直坏到重启（下一条），而且要赶在这次开机的第一个框架流*还没发生*之前（每次开机只允许一个 loader；第二次 init 会死在 `cal_block_ion_alloc: audio ION import failed, rc = -22` → `-12`）。
- **每次开机只能有一个进程把 ACDB loader 初始化成功。** mediaserver 加载完块之后，另一个进程里的第二个 `acdb_loader_init_v2` 会死在 `cal_block_ion_alloc: audio ION import failed, rc = -22` → `voice_alloc_cal … failed` → init `-12`，而第一个进程继续持有那些块。自己驱动 loader 的诊断工具必须跑在一次全新开机上（在第一个框架流之前），否则就等着 `-12` 吧。
- **TX 校准能把采集毒坏到本次开机结束。** 在 maple 上 loader 接受 acdb 4（`send_audio_cal, acdb_id = 4, path = 1, … Topology Id 112fb`），但之后每一次采集 prepare 都死：走 HAL 自己的发送时是 ADM（`adm_callback: cmd = 0x10326 returned error = 0x1`、`msm_pcm_routing_reg_phy_stream: adm open failed copp_idx:-131`、`msm_pcm_capture_prepare: stream reg failed ret:-22`、`ASoC: platform prepare error: -22`），而裸 loader 发送、没有 capture app-type cfg 时则是 SLIM TX 后端放弃（`msm-dai-q6-sb-0-tx: ASoC: cpu DAI prepare error: -131`、`SLIMBUS_0_TX: ASoC: backend prepare failed -131`）——两条路都一样：`AudioRecord` 挂住，tinyalsa 采集以同样方式失败，所以问题在 cal 块，不在 HAL。`kill -9 mediaserver` 释放不掉它们——只有重启，所以任何 TX-cal 实验（包括 `acdbtest --scan`）都该放在一次会话的最后。在 ADM 拓扑不匹配被搞清楚之前，让采集保持未校准；RX 侧不受影响（acdb 15/10 带的是拓扑 `112fc`，播放正常）。
- **`routing=` 是有符号 int。** KitKat 的策略层用 `param.addInt(String8(AudioParameter::keyRouting), (int)newDevice)` 发它（`hardware/libhardware_legacy/audio/AudioPolicyManagerBase.cpp`），所以 `AUDIO_DEVICE_IN_*` 的值到达时是负的（0x80000004 → -2147483644）。用 `str_parms_get_int` 解析，再把 int 转回 `uint32_t`；一个用 `%u` 的发送方反而会溢出成 `0x7fffffff`（INT_MAX）。
- **耳机插孔路由需要一个内核可能并不创建的 switch class 节点。** KitKat 的 `WiredAccessoryManager` 盯的是 `/sys/class/switch/h2w/state`；如果 codec 驱动只注册了 `hdmi`/`lid`/`sim_detect`（maple 的 tasha 内核就是这样），那就永远没有人给插上的耳机发 `routing=`，而 app 也强制不了*输入*设备，因为策略层在 `startInput` 时会重发它自己的输入路由。照样把路由 switch 和它的 acdb id 建起来（`platform.c` 的 `acdb_device_table[]` 里 RX headphones 10、TX headset mic 8），但在有 jack 来源之前把 headset-mic 这条路标成待验证。
- **扬声器 cal 发送时 `ACDB AFE returned = -19` 是无害的。** Android 15 的 loader 对 dev 15 每次发送都会打 `Failed to fetch the lookup information of the device 0000000F` + `ACDB_CMD_GET_AFE_COMMON_TABLE_SIZE Returned = -19` / `ACDB AFE returned = -19`，然后继续走 `AUDIO_SET_AFE_CAL` 和 `send_hw_delay`；yoshino 的 MTP acdbdata 就是没有那个设备的 AFE 公共表。已验证非致命（maple：同一对日志会出现在音频以满电平回环的那些运行里，例如 TEST 52 的视频）。别把它当校准失败去追——真正应用的 AFE cal 是拓扑那份。

## 媒体解码教训（maple，2026-10-19）

- **KitKat 的产品必须提供 `/system/etc/media_codecs.xml`。** 4.4 的 `OMXCodec` 会去问 `MediaCodecList`，后者解析这个文件；AOSP 只为 goldfish/sdk 发了一份（`device/generic/goldfish/camera/media_codecs.xml`，由 `sdk.mk` 引入），真实产品没有。缺了它，`initCheck()` 一直是 `NO_INIT`、`getInstance()` 返回 NULL、`findMatchingCodecs` 一直是空的，于是 `OMXCodec::Create` 对**每一个**压缩 MIME 都返回 NULL。dmesg 里唯一的证据是 `MediaCodecList: unable to open media codecs configuration xml file.`（ALOGW）；那句决定性的 `No matching codecs!` 是 ALOGV，被 `-DNDEBUG` 编译掉了。
- **「音频能用」可能只是说裸 PCM 能用。** `AwesomePlayer::initAudioDecoder` 对 `audio/raw` 绕过 OMX（`mAudioSource = mAudioTrack`），所以 WAV 能放（只经过 extractor + HAL），而 ogg/mp3/aac 是静音的。在声称支持媒体之前，先测一个压缩文件。失败会表现为 `UNKNOWN_ERROR`（0x80000000，java 日志 `error (1, -2147483648)`），对 SoundPool 则表现为 `onLoadSoundEffects(), Error -22 while loading samples`——`MediaPlayerService::decode`/`AudioCache` 把同一个播放器错误映射成 `BAD_VALUE`（-22）。
- **要列 `SoftOMXPlugin` 真正提供的组件。** `frameworks/av/media/libstagefright/omx/SoftOMXPlugin.cpp` 里的表才是真相（组件 → 库 + 角色）：soft MPEG4 库同时注册 `OMX.google.mpeg4.decoder` 和 `OMX.google.h263.decoder`，`vpxdec` 同时注册 vp8/vp9。不要照抄更新设备的 `media_codecs.xml`：在这个移植上，它的 qcom 组件名背后没有 KitKat 的 OMX core。`OMX.google.raw.decoder` 是 `MediaCodecList` 自己加上的，再列一遍就是重复。
- **同一个缺口也会关掉视频解码**（h264/vpx 组件只通过那个 XML 存在），所以没有它的移植也放不了视频——在调试视频*输出*路径之前值得先知道这一点。
- **2026-10-19 在 maple 上验证**，用的是 `devices/maple/kitkat/media/media_codecs.xml`（21 个 `OMX.google.*` 组件，与镜像里 17 个软解码库对应）：Music 的 AudioPreview 通过 HAL 放 mp3 和 ogg（路由 + acdb，没有 `MediaPlayer: error`），440 Hz mp3 的 DMIC 回环读回 440.00 Hz，UI 点击声播放且没有 SoundPool 错误。视频也一样：Gallery 的 `MovieActivity` 播一个 h264+AAC 片段时创建了 `OMX.google.h264.decoder`，全屏渲染测试图（`MediaPlayer: info/warning (3, 0)` = MEDIA_INFO_VIDEO_RENDERING_START），并把它那条 880 Hz 的音轨通过 HAL 回环到 **880.00 Hz**——解码器、GL 合成和音频 sink 在一次测试里全覆盖。maple TEST 52。

## 与旧用户空间并存的新用户空间（taimen；为 maple 做过评估）

Taimen 的移植在 32 位 KitKat 旁边跑了一个 64 位 Android 11 chroot（`/system/v11`），并且为 KitKat 跑不起来的那些守护进程（modem、wifi、sensors、GNSS、NFC）给每个 KitKat HAL 配了一座桥。那套设计*还没有*移植到这里，但它是 maple 剩下每个子系统的参照；它们的代码和我们按子系统做的评估见 [taimen-kitkat-mapping.md](../taimen-kitkat-mapping.zh-CN.md)。可复用的教训：

- **KitKat 的 `toolbox` 没有 `chroot`，它的 `mount` 也不会 bind-mount。** 进去的办法是一个小的静态 helper：`unshare(CLONE_NEWNS)`、把 `/` 设成 private、把 `/dev`、`/proc` 和 `/sys` 整片 bind-mount 进新根、`chroot`，然后用一个干净的环境 exec——刻意*不*传 KitKat 的 `ANDROID_PROPERTY_WORKSPACE`。整片 `/dev` 没问题；把 binder 节点留在外面就不让 HIDL 在里面启动。
- **64 位用户空间可以在 32 位 Android 底下跑**：内核是 64 位的，旧的只是用户空间。用 NDK 构建 chroot 里的程序（helper 静态链接；动态守护进程链到 stage 在 chroot *里面*的新版 bionic），并把新系统自己的 `linker64` 一起带过去——在一个扁平的系统 dump 里它是真实文件，路径是 `system/bin/bootstrap/linker64`，就在 `/apex` 符号链接旁边。
- **整棵树要通过一个假模块（phony module）来发，而不是 `PRODUCT_COPY_FILES`：** `LOCAL_POST_INSTALL_CMD := cp -a <dir> $(TARGET_OUT)/<where>` 能带走空目录和*绝对*符号链接（厂商的 `rfs/` 里全是这种），而拷贝清单对这两类东西是静默无能的。
- **桥的是 HAL 库，不是 HIDL 服务。** vndservicemanager 和 hwservicemanager 在 KitKat 上不存在，所以 HIDL 服务起不来——但它的实现 `.so` 可以被一座桥在进程内 `dlopen`，再由桥通过一个抽象 AF_UNIX socket 重新发布给 KitKat 的 HAL，字段宽度手工定死（32 位和 64 位进程里布局完全一致）。版本错位（NCI 2.0→1.0、camera HAL 3.5→3.0、sensor flush 语义）在桥里翻译，因为那里两边都看得见。
- **`-rdynamic` 可以压过厂商库的符号：** 导出我们自己的 `getRawServiceInternal` 会压过 libhidlbase 的那份，于是 NXP NFC 的 secure-element 查找会快速失败，而不是在一个不存在的 hwservicemanager 上永远等下去。
- **新版的守护进程把日志写到 logdw，不是 kmsg。** Android 8+ 的 liblog 写 `/dev/socket/logdw` 数据报；没有 logd 时 chroot 是沉默的，直到有一个接收者绑定那个 socket 并只把*警告和错误*转发到 `/dev/kmsg`（info 会淹掉内核缓冲）。libhyb 里对应的做法是把 HIDL 的 `getService`/`AServiceManager` 打成桩，立刻返回「没有服务」。
- **在放弃一套 QMI 栈之前，查 `libqmi_cci`，别只查内核配置。** 现代高通用户空间可以是双传输的：maple 的厂商 `libqmi_cci.so` 同时有 `qcci_ipc_router_ops` *和* `qcci_qrtr_ops`，带运行时探测，所以 libqmi_cci 的客户端在无 QRTR 的内核上能回退到旧式 IPC router（静态结论，待验证）。
- **非 root 的 QMI 客户端需要 IPC-router 的安全规则**（`irsc_util <vendor>/etc/sec_config`）。像 `pdserve` 这样的 root 客户端从不会察觉它们；以 `system` 身份跑的守护进程缺了它们就会挂住。
- **modem 的打通顺序很重要：** 手工创建 `/dev/block/bootdevice/by-name` 链接（ueventd 不会）、让 EFS 守护进程和固件服务器跑起来、只在它启动期间把 `firmware_class.path` 指向 modem 分区、并在系统的整个生命期里持有 `/dev/subsys_modem`（maple 的 `modem-hold.sh`，TEST 39，是同一个招数但没有 chroot）。

## 容器坑点（已验证）

- Trusty 镜像需要 `lib32stdc++6 lib32z1`（没有它们 KitKat 的 32 位预编译宿主工具会死）、一个 `python` → `python2.7` 的符号链接，以及 JDK-vendor-check 补丁（Oracle JDK 6 装不上；`patches/kitkat/build-jdk-openjdk6.patch`）。
- `repo sync` **必须**是 `repo init --depth=1` + `repo sync -c --no-tags`，否则会拉整个 AOSP 历史（100+ GB 且还在涨）。
- `TARGET_PREBUILT_KERNEL := vendor/<vendor>/<device>/kernel`（内核是通过 TWRP 从运行中的设备 dump 出来的，和所有 blob 一样不入 git），这样单纯的 `make bootimage` 就能把它和构建出的 ramdisk 一起打包——用户空间打通不需要重建内核。

## 源码与工具链（对照 Donut）

- **分支：** `repo init -u https://android.googlesource.com/platform/manifest -b android-4.4.4_r2` → `aosp-kitkat/`（11 GB+；已 gitignore）。在把脚本定死之前，对着 build numbers 表确认确切的 `_r` rev。
- **需要 64 位宿主**（Gingerbread+ 的规则；Donut 的 i386 chroot **不**适用）。构建配方：Ubuntu **14.04（Trusty）**时代的容器/chroot + **JDK 6** + Make 3.81 + Python 2.7。KitKat 在 `prebuilts/jdk/` 里带了预编译的 OpenJDK 组件供某些步骤使用，但 2.3–4.4 的文档路径仍然是单独装 JDK 6。（Donut：Hardy + JDK 5；KitKat：Trusty + JDK 6。）
- **KitKat 里没有 ARM64。** `TARGET_ARCH := arm64` + `TARGET_2ND_ARCH` 是 Lollipop 5.0 的发明。MSM8998 的打通从 32 位（`armeabi-v7a`）起步。见 `docs/devices/maple/quirks.md` 的阻塞项 1——先探这个，再干别的。
- 宿主 GCC：Trusty 时代的 GCC 4.6/4.8 是安全基线（与 Donut 的 GCC 16 vs `apriori` 失败同一个教训，晚一代）。

## KitKat 构建系统差异（对照 Donut 坑点）

- `lunch full_maple-eng` 的产品发现是同样的形状（`AndroidProducts.mk` → `full_maple.mk`），但 KitKat 的 product 文件用的是更新的 `inherit-product` + `PRODUCT_COPY_FILES` 拆分——对着同步下来的树里的 `build/target/product/generic.mk` 核对，别凭记忆。
- KitKat **有** `run_program`、ext4 的 `format()`、3 个以上参数的 `mount`，以及 Donut 缺的 `write_raw_image` 语义——cooper 的 updater 回移**不**适用。从 KitKat 的 `bootable/recovery/updater` + TWRP 3.x 的预期（API 19 时代）重新推导 updater-script。
- `TARGET_PROVIDES_INIT_RC` 模式仍然适用；KitKat 的 init 语言比 Donut 丰富（更多触发器/标志）——重新审计每条 cooper 时代的假设（`import`、`wait`、`exec` 的语义自 1.6 起都变了）。
- 来自 cooper 的 `preloaded-classes` / provisioning / keymap 教训在精神上适用，但必须重新测量：KitKat 的 Zygote 预加载清单、`Settings.Secure` 和 `.kl` 标志集都与 Donut 不同。
- mkbootimg：KitKat 早于 `Image.gz-dtb`；预期需要 `patches/kitkat/` 里的回移补丁（先例：`patches/donut/mkbootimg-pagesize.patch`）。
- SELinux 在 KitKat 已是 enforcing 时代（Donut 里它是缺席/宽容的）。首次打通很可能需要 permissive + 对着 4.4 内核的安全钩子做策略审计。

- **只要定义了 `LOCAL_DEX_PREOPT` 就会开启预优化（preopt），哪怕值写成 `false`。** KitKat 的构建只要看到这个变量被定义就做预优化；必须保持原样的预编译 app（Open GApps nano，按 Taimen 发布构建的做法）得彻底不定义它。

## 4.4 内核上的 KitKat 用户空间（对照 2.6.35 上的 Donut）

- 与 cooper 同一类问题（新内核、远古用户空间），只是晚一代：对着 4.4 的 uevent 审计 ueventd 冷启动/节点创建、cgroups、netd/vold、固件加载路径，以及 `lowmemorykiller` 调优。
- cooper 那套 vold/adbd/rild 崩溃循环分诊在这里适用：给 NULL 的 uevent 字段加保护，pty 出问题就用分离管道法诊断 adbd，在 SoC 有 RIL 库之前把 `ril-daemon` 注释掉。

## 容器坑点（构建后待填）

- （空——踩到 Trusty-apt/JDK6/debootstrap 的问题就像 `docs/advanced/porting-notes/donut.md` 记 Hardy 那样记在这里。）
- **在这些移植上测量面板管线（fb0 dump、alpha、睡眠）**（maple TEST 34/35，每个坑都花了真实时间）：fb 是 RGBA，像素带 alpha 0 很正常——全零帧是*透明黑*，而它的 RGBA PNG 在多数查看器里会渲染成**白色**；得出任何结论之前先用 `format=rgb24`（ffmpeg）解码 fb dump。睡眠的屏幕会把最后一帧 BLANK 帧（全零）留在 fb0 里。另外，「白屏/黑屏冻结」但 UI 进程还活着、只是空闲的情形通常就是屏幕睡了：这些 KitKat 移植用 keyguard 窗口的 `userActivityTimeout`（10 秒）封顶息屏超时，而**触摸输入不会唤醒屏幕**——测试脚本必须检查 `mScreenOn` 并用电源/菜单键唤醒，否则会花一小时「测试」一块黑屏。还有：`screencap` 在 framebuffer 呈现的栈上可能返回固定不变的图像（用 fb0 dump），而 `input keyevent 26` 是切换，不是「打开」。

- **SERVREG_LOC（QMI 0x40）可以由 32 位用户空间通过旧式 IPC Router socket API 提供服务**（maple TEST 40，2026-10-17）：不需要 chroot——尽管官方原厂的 64 位 `pd-mapper` 看起来是唯一的路子（它链接的是双传输的 `libqmi_cci`，但正是早先那个「无 QRTR」的结论才让这个守护进程存在），内核的 `service-locator` 客户端（`get_service_location` → `qmi_svc_event_notifier_register(0x40, 1, 1)`）只需要**某个**服务端绑定在 `AF_MSM_IPC`（family 27，`SOCK_DGRAM`）上，名字为 `{service=0x40, instance=BUILD_INSTANCE_ID(1,1)=0x0101}`。一个小的静态 musl 二进制（`devices/maple/kitkat/pdserve/pdserve.c`）做到了：它绑定那个名字，接收内核的 `GET_DOMAIN_LIST` 请求（msg 0x21），并用从 modem 分区的 `.jsn` 文件转录来的 domain 列表作答。线格式是标准的 QMI TLV 编码——精确的 `elem_info` 数组（`qmi_servreg_loc_get_domain_list_resp_msg_v01_ei`）见 `drivers/soc/qcom/service-locator-private.h`，TLV/字符串编码规则见 `lib/qmi_encdec.c`（顶层字符串是裸字节；嵌套字符串是 `[u8 len][bytes]`）。这解除了 PD 重启链（icnss、audio_pdr、slimbus）的阻塞，并让 modem 的 TMS 能查询 AP 的 domain 列表。注意：这个移植上的 modem 固件仍每约 41 秒崩一次（err-fatal interrupt，无 SMEM reason），所以端到端 Wi-Fi 尚未验证——这个崩溃与 locator 无关，很可能需要一个本移植没有的保活（rild）。
